# Arbiter

![Arbiter Dashboard](web/screenshot.png)
Arbiter is a durable double-entry ledger and payment settlement engine built for fintech system-design interviews and senior engineering review. It demonstrates the core layer behind bank payment systems: every movement of money is represented as immutable journal entries, every duplicate request is idempotent, every settlement reconciles, and every benchmark claim is generated by a local CLI run.

This repository intentionally avoids placeholder infrastructure claims. The current implementation is a production-style local core using Java 21 and a durable append-only file ledger with checksum verification and `fsync`. The documented production upgrade path maps the same interfaces to DynamoDB transactions, Kafka audit topics, Redis idempotency, and S3 WORM archival.

## What This Proves

- Double-entry accounting invariant: each posted transaction creates one debit leg and one credit leg that sum to zero.
- Durable append-only storage: ledger records are written to disk with checksums and forced to stable storage before state is applied.
- Idempotency: repeated `EndToEndId` values return `DUPLICATE` and do not create extra journal entries.
- Settlement decision path: payment initiation runs through authorize, fraud score, ledger post, audit publish, and reconciliation.
- ISO 20022 entry point: `pain.001`-style XML payment messages are parsed and settled.
- Brutal local evidence: tests and benchmarks create real ledger files, not mocked repository calls.
- Full-stack demo: the backend serves a populated frontend console at `/` and the frontend calls the backend APIs directly.

## Architecture

```text
Browser console
  -> Java HTTP API
    -> SettlementSaga
      -> RuleBasedFraudScorer
      -> LedgerService
        -> FileLedgerRepository
          -> append-only ledger.log with checksum and fsync
      -> AuditEventPublisher
    -> ReconciliationService
```

Production mapping:

| Current component | Production equivalent |
| --- | --- |
| `FileLedgerRepository` | DynamoDB single-table ledger using conditional `TransactWriteItems` |
| `AuditEventPublisher` | Kafka topics for journal entries, payment status, immutable audit |
| `RuleBasedFraudScorer` | Python FastAPI fraud sidecar with feature store and Isolation Forest |
| `Iso20022MessageParser` | JAXB parser with official ISO 20022 schemas |
| Java `HttpServer` | Spring Boot 3 REST/gRPC service |
| `benchmark-results` CLI artifacts | CI benchmark gate plus Gatling report |

## Run Locally

Requirements:

- JDK 21 or newer
- Bash
- No Maven, Gradle, Node, database, or package install required

Commands:

```bash
./scripts/test.sh
./scripts/brutal-test.sh
./scripts/run.sh
```

Open the website:

```text
http://localhost:8080
```

The backend persists its ledger to:

```text
data/ledger.log
```

To start with an isolated data directory:

```bash
java -Darbiter.data.dir=/tmp/arbiter-demo -cp out/classes com.arbiter.ArbiterApplication
```

## Backend and Frontend Connection

The frontend is served by the Java backend from the `web/` directory. There is no separate frontend server.

Connection flow:

```text
GET  /                    -> web/index.html
GET  /styles.css           -> web/styles.css
GET  /app.js               -> web/app.js
GET  /architecture.svg     -> web/architecture.svg
GET  /health               -> backend health check
GET  /accounts             -> frontend account table
POST /accounts             -> frontend account creation form
POST /payments             -> frontend settlement form
POST /payments/iso20022    -> XML payment endpoint
GET  /reconcile            -> frontend reconciliation card
GET  /audit                -> frontend audit event list
GET  /benchmarks/latest    -> frontend benchmark metric cards
```

Because the frontend and backend share the same origin, browser requests use relative paths such as `/payments`. No CORS setup is required for local use.

## API Examples

Create accounts:

```bash
curl -s -X POST http://localhost:8080/accounts \
  -H 'content-type: application/json' \
  -d '{"accountId":"CustomerA","currency":"USD","openingBalance":"1000.00"}'

curl -s -X POST http://localhost:8080/accounts \
  -H 'content-type: application/json' \
  -d '{"accountId":"CustomerB","currency":"USD","openingBalance":"100.00"}'
```

Settle a payment:

```bash
curl -s -X POST http://localhost:8080/payments \
  -H 'content-type: application/json' \
  -d '{"endToEndId":"E2E-001","debtorAccount":"CustomerA","creditorAccount":"CustomerB","amount":"125.00","currency":"USD","purposeCode":"GDDS"}'
```

Submit the same request again to verify idempotency:

```bash
curl -s -X POST http://localhost:8080/payments \
  -H 'content-type: application/json' \
  -d '{"endToEndId":"E2E-001","debtorAccount":"CustomerA","creditorAccount":"CustomerB","amount":"125.00","currency":"USD","purposeCode":"GDDS"}'
```

Check reconciliation:

```bash
curl -s http://localhost:8080/reconcile
```

Submit ISO 20022-style XML:

```bash
curl -s -X POST http://localhost:8080/payments/iso20022 \
  -H 'content-type: application/xml' \
  -d '<Document><CstmrCdtTrfInitn><PmtInf><CdtTrfTxInf><PmtId><EndToEndId>E2E-ISO-001</EndToEndId></PmtId><Amt><InstdAmt Ccy="USD">12.34</InstdAmt></Amt><Dbtr><Nm>CustomerA</Nm></Dbtr><Cdtr><Nm>CustomerB</Nm></Cdtr><Purp><Cd>GDDS</Cd></Purp></CdtTrfTxInf></PmtInf></CstmrCdtTrfInitn></Document>'
```

## Acceptance Tests

`./scripts/test.sh` currently verifies:

- Randomized double-entry invariant across 2,000 settlements.
- Idempotency prevents duplicate journal entries.
- Journal entries cannot be overwritten.
- Fraud decline happens before settlement finality.
- ISO 20022 parser extracts `EndToEndId` and instructed amount.
- Concurrent debits cannot overdraw an account.
- Concurrent duplicate submissions post exactly one double-entry pair.
- Durable recovery rebuilds account balances and transaction history from `ledger.log`.

`./scripts/brutal-test.sh` runs those tests, then executes the benchmark that writes real durable ledger records to disk.

## Security and Reliability Controls

- Strict account, currency, amount, purpose, and idempotency-key validation.
- Request body limit of 64 KB.
- XML parser disables external document type declarations.
- Security headers on HTTP responses: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Cache-Control`.
- Append-only ledger records include CRC32 checksums and fail startup replay on corruption.
- Atomic repository method validates duplicate transaction, double-entry sum, account currency, and available funds inside the synchronized write path.

## Honest Production Gap

This repository is production-ready as a local portfolio core, not as a regulated bank deployment. Before real money or regulated traffic, implement and verify:

- DynamoDB `TransactWriteItems` repository with conditional writes.
- Kafka audit publisher with exactly-once producer configuration.
- Redis-backed idempotency cache with durable fallback.
- Official ISO 20022 schema validation.
- Authentication, authorization, tenant isolation, and signed operator actions.
- S3 Object Lock archive with retention policy.
- OpenTelemetry traces exported to a real collector.
- CI pipeline with benchmark thresholds and artifact retention.

That gap is intentional and visible. The value of this project is that the core invariants are implemented and measured now, while the infrastructure migration path is explicit.
